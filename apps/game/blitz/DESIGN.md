## 一句话定位

**2.5D 横版**（belt-scroll）仙侠动作 RPG。地面有 **X（左右）+ Z（纵深）两条轴**，移动八方向、
朝向**四向吸附**（左 / 右 / 上=背面 / 下=正面），跳跃是一个真正的战术维度（Y 高度）。

玩家在**固定地图**（分块加载）里探索，打怪掉落**永久装备/技能**，死亡在**复活点**复活（低惩罚），
通过**触发 NPC 对话**推进剧情。战斗偏动作向：高频操作、强反馈、技能丰富，让玩家有多种方式打怪。

### 玩法重心：技能主导，动作为辅（2026-10-30 定）

这是对「2D + 四向朝向装不下深动作博弈」的诚实承认，不是降级：

- **纯动作博弈**（立回、骗刀、目押、帧级对拆）需要海量招式组合，2D 逐帧美术撑不起这个量；
  四向朝向又限制了绕后/换向这类空间博弈。硬推动作深度，结果会是「招式少、手感还一般」。
- **所以深度交给技能构筑**：同一套装备 × 不同技能 = 不同打法（见「技能系统」，
  以及下面的「博弈从哪来：读招 → 应对 → 代价」）。
  动作用来服务技能的释放节奏（起手 / 蓄力 / 收势 / 位移），不追求招式表。
- **连带的美术结论**：画面上吃工的是**技能表现（VFX）**，不是角色动作。角色动作帧因此可以短
  （起手 3~5 帧 + 收势），表现力交给特效、顿帧、屏震。这正好是 2D 像素 + shader 的强项。
- **内容的真正大头是 Boss 的技能组**：小兵多没关系（共享骨架/模板），但每个 Boss 的每个技能
  都要独立的表现和预警 —— 这条直接决定美术路线怎么选（见 [ART_ROUTE_DECISION.md §12](ART_ROUTE_DECISION.md)）。

> 技能要「有点多」，就必须是**数据驱动**的：`AttackShape` 已经解决了判定（形状+偏移+高度带+延迟），
> 表现层也应该跟上是同一套思路 —— 一个 `SkillDef` 描述 { 形状, 延迟, vfx_id, 调色板偏移, 顿帧, 屏震 }，
> 新技能 = 表里加一行，不是新写代码 + 新画一套图。

## 为什么是「2.5D 横版」，而不是等距 / 真 3D

这一节是**用两轮实测换来的结论**，不是拍脑袋。走错的那一轮值得完整记下来。

### 走过的路

| 版本 | 视角 | 结果 |
|------|------|------|
| v0.1 | 2D 横版**平台跳跃** | 只有左右 + 跳，没有纵深走位，探索感太薄 |
| v0.2–v0.3 | **等距** 3/4 | 美术看起来好，但**操作和地面在说两种语言**：按 W 走直线，脚下的地砖却是斜的，怎么走都错开半格 |
| **v0.4 ✅** | **2.5D 横版（belt-scroll）** | 地面两轴与输入天然一致；先按「朝向只有左右」落地 |
| **v0.5 ✅** | 同上 + **四向朝向** | 实测发现纵向移动时侧着身子很怪 → 补上背面/正面两视图，美术从 2 组变 3 组 |

### 等距错在哪（不是八向输入的问题）

等距的实现是「**屏幕 XY 就是世界 XY**，只在 `_draw()` 里把地面压扁画成菱形」。
于是：

- 输入 `Input.get_vector(...)` 直接是**屏幕横竖**；
- 地面网格的两根轴却是屏幕的**斜线**；
- 角色位置、速度、判定框全是未投影的屏幕坐标。

**「输入映射到等距轴」这件事在 Model A 下根本做不到** —— 两种坐标系从来没有统一过。
表现就是「跟野怪对不上」：你觉得对着它，判定框却偏在一边。

### 纠正 v0.2 写下的两个错误论据

| v0.2 当时的说法 | 事实 |
|---|---|
| 「2D 横版只有左右 + 跳，装不下 XY 平面走位」 | 那是**平台跳跃**版横版。**belt-scroll**（DNF / 三国战纪 / 怒之铁拳）有 **X + Z 两条地面轴**，平面走位一直都在，只是轴名叫「左右 + 纵深」 |
| 「真 2.5D 要 4-8 方向资产，solo 扛不住」 | belt-scroll 的朝向是**四向**（左 / 右 / 背 / 正），美术 **3 组**（侧视一张镜像出左右 + 背面 + 正面），只是等距八向（8 组）的 **3/8**。等距才是那个需要八向资产的方案。（v0.4 时算的「2 组 / 便宜 4 倍」是只做左右时代的账，v0.5 补上纵向视图后作废） |

### 为什么不是真 3D

建模 / 绑骨 / 贴图 / 动画 / 光照是三条路线里最贵的，且偏离「纯 2D 手绘」的美术规划。
2.5D 横版用「纯 2D 精灵 + 纵深压缩 + Y-sort」拿到立体的观感，成本是 3D 的零头。

### 代价（诚实地写下来）

- **深度遮挡比等距弱**：只有前后，没有「左后被墙挡住」这类构图。
- **Z 轴的表现力有限**：纵深是「可以站的一行行」，不是自由移动的平面。这与「每个招式自带形状、范围在 XZ 平面上」的判定模型正好匹配。
- **大地图探索还没想清楚**：先用「城镇 + 房间副本」的房间制装下（见下节）。

## 坐标模型（整个项目的地基）

```
世界 = 3 个数:  x (左右)   z (纵深)   height (离地高度)
引擎里存:      global_position = Vector2(x, -z)        ← 纵深吃负 Y
屏幕显示:      y_screen = -z × DEPTH_SCALE (0.5)       ← 纵深压扁一半
高度:          height 单独一个标量, 只用在 _draw() 里
```

三个白送的好处：

1. **Y-sort 一行不用改** —— 「屏幕 Y 越大越靠前」正好就是纵深排序。
2. **重力只作用在 `height` 上，永远不碰 `position.y`** —— 这条是铁律。写成
   `velocity.y += gravity * delta` 角色会一边跳一边往屏幕深处漂；Y-sort 也会按抬起来之后的
   y 排序，一跳就钻到别人后面。**能跑、能跳、看起来也对，所以是静默 bug。**
3. **跳跃是纯加法** —— 身体画在「脚底 + (0, -height)」，影子留在脚底。现有「原点在脚底」的
   约定天然兼容。

**唯一桥：** [scripts/belt_space.gd](scripts/belt_space.gd)（`to_screen` / `to_world` /
`ground_circle` / `ground_circle_shape` / `limit_world_speed`）。任何别处自己手写投影数学，
都是在制造第二个真相。

## 核心循环

```
探索地图 → 打怪 → 掉装备/技能/资源 → 变强 → 推进地图 → 触发剧情
     ↑                                              │
     └────────── 死亡 → 复活点复活（低惩罚）────────┘
```

- **死亡不重开**（非肉鸽）：死亡 → 在最近的复活点复活，已获得的装备/资源**永久保留**
- **死亡惩罚低**（具体待定）：倾向「掉一点资源/经验」而非「掉装备」，避免挫败
- **地图固定**：不做随机地图，玩家按顺序探索一张张分块地图
- **资源是仙侠的灵魂**：修为、灵石、丹药、装备、功法都是可积累的资源

## 地图结构（怪猎式分块 · 暂定房间制）

| 特性 | 说明 |
|------|------|
| 结构 | 世界由**多张固定小地图**组成，进入边界触发加载切换到下一张 |
| 连接 | 类似怪猎/黑魂——地图间有明确连接点（山道、洞口、传送阵） |
| 复活点 | 每张地图设 1-2 个复活点（蒲团/石碑/阵眼），死亡在此复活 |
| Boss 区 | 关键地图设 Boss 房，进门即战 |
| 探索节奏 | 固定但非线性——部分地图可解锁捷径回环（回到已探索区） |

> ⚠️ **大地图探索的具体形态还没拍板**（用户原话：「还没想清楚」）。v0.4 只保证
> 「城镇 + 房间副本」的房间制**装得下**，不提前锁死结构。
>
> 设计原则：**小地图 + 明确连接 + 回环捷径**，让玩家「一个个探索」有进度感，又不用做无缝大世界。

## 战斗系统（技能主导 · 动作执行）

### 目标：高频操作 + 强反馈 + 有挑战性

玩家需要频繁做决策（打 / 躲 / 挡 / 跳 / 放技能），每一次操作都有明确的即时反馈。

### 博弈从哪来：读招 → 应对 → 代价（2026-10-30 定）

**不是「连段越多越有博弈」。** 博弈的定义是：玩家必须在信息不完整时做**有代价的选择**。
三层缺一不可：

1. **读招** —— 敌人给出可读的信号（预警形状 + 起手动作 + 音效），玩家能预判但会被骗。
2. **应对** —— 同一招有 **≥2 种有效答案**，而且答案不同：闪 / 挡 / 跳 / 反打 / 放技能。
3. **代价** —— 每种答案都失去点什么：位置、精力、输出窗口。**没有代价的选择不是选择，是流程。**

#### 为什么选技能主导，不是动作连招主导

| | 连招主导 | **技能主导** |
|---|---|---|
| 深度来源 | 执行精度（帧级、手速、肌肉记忆） | **决策**（什么时候放、放哪里、放弃什么） |
| 敌人要多少内容 | 每招都要独立动画 + 帧数据 + 破绽 | 读得懂的招 + 几个应对出口 |
| solo 成本 | 高：每多一招敌人都是新美术 + 新手感调 | 低：技能是数据，敌人招是模板 + 变体 |
| 和仙侠题材 | 只是武侠 | **阵法 / 护盾 / 剑阵就是题材本身** |
| 现有代码 | 要新写连段系统 | **已经在支持**：`AttackShape`（形状/延迟/高度带）+ 预警 + 格挡半平面 + 跳跃躲低扫 |

> 一句话：**动作是「怎么打」，技能是「打什么、什么时候打、放弃什么」。**
> 前者靠手，后者靠脑子 —— 要的博弈在后者。连招仍然保留，但它是**表达层**（打得好不好看），
> 不是**深度层**（打得对不对）。

#### 最常见的退化：技能变成数值选美

如果技能之间没有互斥的代价，玩法会退化成「哪个 DPS 高就用哪个」，博弈直接消失。
守住三条：

- **资源同池**：真气 / 精力只有一个池 —— 放技能就挡不了，挡就得放弃输出。
- **位形竞争**：阵法占同一块地/同一个「布阵」名额，两个阵不能叠。
- **敌人会破**：每个控场技能都要有敌人的反制（位移破阵、净化、无视护盾的招）。

**每个新技能必须回答三个问题，答不上就只是数值：**

1. 它对应哪一类敌人招？（它解决什么问题）
2. 用错的时候你损失什么？（代价）
3. 敌人怎么破它？（反制）

> **[COMBAT_MATRIX.md](COMBAT_MATRIX.md)**。加技能前先去那里加一列。

### 基础操作（v0.4 实装值）

| 操作 | 按键 | 说明 |
|------|------|------|
| 移动 | WASD / 方向键 | **X（左右）+ Z（纵深）** 两条地面轴 |
| 跳跃 | **C** | 重力 1400 / 起跳速度 520 / 满跳高度 ≈96.6；可变跳跃高度（松键截断）；**落地硬直 0.18s**（见下） |
| 轻击 | J / 鼠标左键 | 扇形扫击，伤害 1，硬直 0.15s |
| 重击 | **按住** K / 鼠标右键蓄力，松开挥出 | 0.75s 蓄满；伤害 2→4；**满蓄破霸体** |
| 技能（落雷） | U | 身前一格半处圆形 AoE，**延迟 0.38s 生效**（能走出去） |
| 技能（护体罡气） | **I** | 精力 30 / 持续 1.5s / 冷却 3s；**吃一次伤害**，期间**不能出手** |
| 技能（剑阵） | **O** | 精力 30 / 冷却 4.5s；**在脚下落阵，持续 3s 留在原地**，范围内每 0.5s 伤害 1；追兵绕开 |
| 闪避 | Space | 无敌帧冲刺，消耗精力 25 |
| 格挡 | **按住** Shift / L | **前后半平面**免伤（按朝向分，见上面「朝向模型」），持续耗精力 + 每次硬挡扣 20 |
| 精准格挡 | 按下格挡键的**那一瞬间**（0.16s 窗口） | 零伤零耗 + 攻击者硬直 1.2s（反击窗口） |
| 调试面板 | F1 | 范围可视化 / 纵深泳道 / 按键 |
| 重开 | R / Enter | 开发期用 |

### 操作规则（v0.5）

1. **移动八方向、朝向四向吸附。** 走上下也会转身 —— 往上走看**背面**，往下走看**正面**。
   > v0.4 的「只按上下不转身」被用户实测否掉了：纵向移动时侧着身子走看着像滑冰。
   > 换向有 **1.25 的迟滞**（`Facing.choose`）：斜向走位时朝向不会逐帧乱翻；
   > **出招/起手期间锁死朝向**，中途按上下不会把已经挥出去的判定转走。
2. **格挡只挡面朝的那一侧；垂直于朝向的方向算正面。**
   > 这正是用户要的效果：「站得比我靠前/靠后一点，攻击一样得挡得住」。
   > 判定是 `(受击方向 · 朝向) >= 0` 一次点乘，**没有可以调窄的旋钮**。
   > 面朝左右时 = 只看 `dx` 的符号（v0.4 的行为原样保留）；面朝上下时同一个式子自动转成
   > 「只看 `dz` 的符号」，垂直那条线照样算正面。
3. **格挡有 0.45s 的精准窗口冷却。**
   > 没有它的话最优解是疯狂连点 Shift，每一下都重开窗口 ——「精准格挡」退化成没有代价的按键宏。
4. **蓄力时可以 50% 速度慢走**（不是原地定身）。
   > 定身会让蓄力在走位为主的战斗里几乎用不出来 —— 敌人一起手你就必须走。

### v0.6 的两个「代价」机制（`player.gd`，2026-11-10）

它们不是新玩法，是**把已经太好的答案补上代价** —— 来自 [COMBAT_MATRIX.md](COMBAT_MATRIX.md) §3：

| 机制 | 改掉了什么 | 代价 | 为什么这么设计 |
|---|---|---|---|
| **落地硬直** 0.18s | 跳跃曾是躲横扫的**零代价**答案（跳高 96 > 高度带 40） | 落地后 0.18s 内**不能进攻**；移动 ×0.7 | 锁的**只是进攻** —— 跳跃/闪避/格挡照常可用。锁「一切」会变成卡顿感，锁进攻才是「用输出窗口换安全」 |
| **护体罡气** | 读不准时的**兜底**（原本只能硬吃或格挡） | 精力 30 + 1.5s **不能输出** + 3s 冷却 | 吃完一次伤害就消失 —— 只能挡一次，不是无敌；和落雷（35 精力）互斥，是同一管精力的两种花法 |

> 两条都遵循同一条判据：**新增的应对必须能从「时间 / 资源 / 位形」里挑一样当代价。**
> 三者都给不出来的答案，就是下一个退化格子。见 DESIGN.md「博弈从哪来」与 COMBAT_MATRIX.md。

### v0.7 剑阵 —— 第一个「布置」类技能（`scripts/fx/sword_array.gd`，2026-11-10）

v0.6 的罡气填的是「兜底」，不是「布置」。[COMBAT_MATRIX.md](COMBAT_MATRIX.md) §3 ③ 指出的空格子是：
**玩家的七个应对全是即时反应，没有一个能改变未来两秒的战场状态。** 剑阵填的就是这一格。

| 项 | 值 |
|---|---|
| 半径 | 76 世界单位（≈ 1.2 格） |
| 持续 | 3s（`duration`） |
| 跳伤 | 每 0.5s，伤害 1，落阵当帧先跳一次 → 全程 6 跳 |
| 代价 | 精力 30 + 施放硬直 0.25s（锁进攻，不锁走位）+ 冷却 4.5s |
| 位置 | **留在原地**，不跟随玩家 —— 这是「布置」与「光环」的分界线 |

三条不能改的设计约束（改了就退化，且**都不会报错**）：

1. **DoT 走 `take_dot`，不走 `take_damage`。** 后者每跳都会硬直 + 击退 →
   剑阵自己把敌人赶出圈外，而且敌人被永久控制，「读招」机制直接架空的。
   **剑阵逼位，不逼失误。**
2. **玩家站在阵里时，敌人不再回避、直接冲进来。** 否则圈内就是零代价安全区 ——
   玩家站进去什么都不用做。现在的规则让「站自己阵里」成为一个要付代价的选择；
   正确用法是**插阵 → 退出去**。
3. **避开的判据是「直线走过去会不会踩进去」，不是「离阵多近」。** 前者是一个几何问题，
   没有需要调的感知半径；而且一旦切向绕行让路径擦不到阵，下一帧自动恢复直线追击，
   **不会出现在阵边绕一辈子**。

> 和罡气一样，它**不进 `ATTACKING` 状态**、没有 `AttackKind` —— 玩家身上的状态只有
> 一个冷却计时器和一个 0.25s 的施放锁。阵的寿命、跳伤、绘制全在 `SwordArray` 自己身上。
> 玩家死了阵还在（场景物件，不是玩家状态），这让「先手布置」有投资的味道。

> **被删掉的一条：** v0.3 的「格挡时朝向跟随鼠标」。
> 它不是手感问题，是**等距逼出来的补丁**：朝向只在移动时更新，那么「站着举盾 → 敌人绕到背后」
> 就必然无解。而横版里朝向由**移动方向**吸附，鼠标在角色正上方时该朝哪**没有答案** ——
> 这个补丁连同 `block_aim_override` 出口一起删掉了。

### v0.8 程序化骨架：玩家 + 敌人（`scripts/visual/player_rig.gd` · `enemy_rig.gd`，2026-11-10 ~ 11）

零美术前提下的「上骨骼」：玩家从「一块会滑动的色块」变成**有腿、有手、有 14 个动作**的小人。
骨架是 `RefCounted` 纯数学（不进场景树、不画一笔），`player.gd` 只负责取值、配色和绘制。
**将来的美术资源替换的正是这一层**：`(anim_state(), anim_phase())` 就是 `SpriteFrames` 的动画名 + 帧进度。

#### 骨骼与角度约定

| 段 | 长 | 段 | 长 |
|---|---|---|---|
| 躯干 | 12.0 | 上臂 / 前臂 | 9.0 / 9.0 |
| 颈 / 头 | 3.0 / 6.0 | 大腿 / 小腿 | 12.5 / 13.0 |
| 头半径 | 6.8 | 脚长 / 脚厚 | 6.5 / 3.5 |

角度是**绝对角**：`dir_of(a) = (sin a, −cos a)` —— `0` = 正上，`+π/2` = 正前（朝右），`π` = 正下。
姿态表里写的是「手在哪、刀朝哪」这种整句，**不是**父子角度累加。
累加式骨架错一个符号不会报错，只会让某个关节朝反方向转；绝对角没有「加」这一步，也就没有这一步可错。

#### 五个结构性决定

1. **只做朝右的骨架，朝左靠绘制镜像。** `_draw()` 里 `draw_set_transform(..., Vector2(f, squash))`，
   `f = _side_facing()`。老代码在每个向量上乘 `f`，漏乘一处就是「朝左时脸朝后」——
   现在镜像只发生在一个地方，**漏乘在结构上不可能**。同理：绘制函数里出现 `f` 就是双重镜像 bug。
2. **腿用两骨 IK，不是纯角度。** 纯角度摆腿在跨步最大那一帧脚必然离地（腿长固定、胯高固定、
   落点却在前后 8px 处），画面上是「人在地上飘」。`ik2()` 余弦定理由脚踝反推膝盖，
   距离先钳到 `[|l1−l2|, l1+l2]` —— 够不到时腿保持原长，**不会出 NaN**
   （NaN 进 `draw_colored_polygon` 是静默不画，一帧里角色整个消失）。
   跑步落点 `_run_foot(th) = (8cos th, −3.5 + 7.5·min(0, sin th))`：支撑期 sin≥0 脚贴地从前往后，
   摆动期 sin<0 抬脚从后往前。胯部起伏 `+1.6·|cos th|` —— **跨步最大时最低**，写反 IK 会把脚拽离地面。
3. **纵深压扁只压「方向增量」，不压「横向站位」。** 背/正面时肩髋必须在身体两侧
   （`lat_arm = 7.0`、`lat_hip = 4.6`；侧视只有 `1.2` / `1.6`），只有从关节点往外伸的
   `dir × 长度` 的 x 分量乘 `0.42`。第一版是「解算完把所有点统一乘 x」，结果两条手臂被压进躯干中线，
   从背后看是「一个布口袋顶着一颗头」。这种错**截图之外看不出来**，自检现在有一条守着它。
4. **刀的握点 = 持剑手手心**（`grip = hand_near`），不是单独摆出来的点。
   单独摆的话手一动刀就脱手悬空 —— 画面上像「刀在飘」，不报错，而且只有动起来才明显。
5. **动画时钟 = 玩法计时器，不是第二个时钟。** `anim_state()` 读 `state` / `_attack_kind` /
   `_grounded` / `_height_vel` / `_landing_timer` / `_cast_lock_timer` / `_hit_stun_timer`；
   `anim_phase()` 读 `_walk_phase` / `_attack_timer/_attack_total` / `charge_ratio()`。
   唯一的新时钟 `_anim_clock` 只喂待机/格挡的呼吸 —— **绝不参与判定或状态**。
   两个时钟一旦不同步，症状是「动作和判定各走各的」，且只在掉帧时出现。

#### 动作表（14 个）

| 类 | 动作 | 关键读法 |
|---|---|---|
| 移动 | IDLE / RUN | RUN：交叉步 + 抬脚 + 反相摆臂；持剑手摆幅只有一半 |
| 空中 | JUMP_RISE / JUMP_FALL / LAND | 上升**收腿**、下落**伸腿**、落地**下蹲**；三帧互相可辨认，玩家分得清「还能不能跳」 |
| 攻击 | LIGHT / HEAVY_CHARGE / HEAVY_SWING | 轻击 = 水平横劈（刀扫过身前）；重击 = 蓄力把刀拉到身后、再竖直劈到身前，刀更长（33 vs 26） |
| 施法 | CAST_LIGHTNING / CAST_SWORD_ARRAY | 落雷 = 举剑过顶、副手按胸；剑阵 = 刀尖朝下插地、身体前躬 |
| 防御 | BLOCK | 刀垂到盾后（不再从盾上方戳出来） |
| 受创 | HIT / DASH / GUARD_BROKEN | 受击后折；冲刺 = 前倾低姿；破防 = 大幅度后仰败势 |

#### 绘制顺序（遮挡关系）

```
侧视    : 远臂 → 远腿 → 近腿 → 袍身 → 头 → 近臂 → 刀
背/正面 : 远腿 → 近腿 → 袍身 → 远臂 → 头 → 近臂 → 刀
```

侧视里远臂在躯干后面，该被袍子盖住；正面/背面看两只手臂都在身体两侧、比躯干更靠近镜头，
**必须画在袍子之后**，否则远臂整条消失，只剩「独臂人」。腿永远压在袍子底下（道袍不是开衩裙），
只从下摆以下露出小腿和靴子；背/正面时脚掌画成脚背（横矩形居中），不再沿用侧视的「朝前伸」。

#### 敌人：同一套架构，另一副骨头（`scripts/visual/enemy_rig.gd`）

敌人也从「梯形身体 + 一颗头 + 一只爪子」换成了骨架。它**不复用 `PlayerRig` 的姿态表**，
只复用两个静态工具：`ik2()` 和 `curve()`（`EnemyRig` 直接转调 `PlayerRig.ik2`，全仓库只有一份 IK）。
身体是**前倾的妖兽**：躯干前扑、**逆关节腿**、双爪、两节尾巴、角与背刺。

| 段 | 长 | 段 | 长 |
|---|---|---|---|
| 躯干 | 13.5 | 颈 / 头 / 头半径 | 3.5 / 4.5 / 7.0 |
| 上臂 / 前臂 / 爪 | 8.0 / 7.5 / 6.0 | 大腿 / 小腿 | 10.5 / 12.0 |
| 脚长 / 脚厚 | 7.0 / 3.0 | 尾（两节） | 7.0 / 6.0 |

三个只在敌人身上成立的决定：

1. **逆关节腿（digitigrade）。** 人的膝盖朝前，妖兽的膝盖朝后。IK 走 `bend_forward = false`；
   角度模式下对应的是大腿 `PI + k`、小腿 `PI − k` —— **和人腿正好相反**。
   两条路径（待机走角度、移动走 IK）必须一致，否则换动作时膝盖会突然弹到另一侧。
   自检直接断言「膝在髋踝中点之后」，不靠肉眼。
   腿长与 `PELVIS_Y = −23.5` 是一对：改一个不改另一个，妖兽会悬空或陷进地里。
2. **爪的方向 = 前臂方向。** `claw = hand + dir(forearm) × CLAW_LEN`，不是独立摆出来的点 ——
   和玩家「刀握在手心」同一个理由：独立点一动就脱手，画面上是「爪子在飘」。
   同一方向也决定手前那两根分叉指爪的朝向，爪和臂始终连成一条。
3. **长硬直压过出招相位。** `anim_state()` 里 `STAGGER` 排在 `attack_phase` **之前**：
   一个在起手时被精准格挡的敌人，身体必须立刻演「被打断」，而不是继续把起手演完。
   这个顺序写反不会报错，只会让玩家觉得「我格挡成功了但它还是打出来了」。

| 动作（7 个） | 关键读法 |
|---|---|
| IDLE / MOVE | MOVE 的步频由**世界速度**驱动（`screen_speed_to_world`），不是屏幕像素速度 |
| WINDUP / STRIKE / RECOVER | 起手 = 后仰 + 爪拉到身后 + 张嘴；命中 = 前扑 + 爪甩到最前（越过胸口 8px 以上）；收招 = 跟随动作 |
| STUN / STAGGER | 短硬直 = 后仰甩手；长硬直 = **重心下沉**（骨盆比 STUN 低 3px 以上）+ 爪撑地 + 低头 —— 一眼看出「现在是奖励窗口」 |

绘制顺序（遮挡）：

```
侧视    : 尾 → 远臂 → 远腿 → 近腿 → 躯干 → 头 → 近臂
背/正面 : 尾 → 远腿 → 近腿 → 躯干 → 远臂 → 头 → 近臂
```

侧视远臂在躯干后面；正/背面时两只手臂在身体两侧、比躯干更靠近镜头，必须画在躯干之后。
尾巴永远最先画（它在身体最后面）。血条抬到 `−62` —— 角把头顶抬到了约 `−57`，原来的 `−50` 会压进角里。

> **美术替换接缝与玩家完全相同**：`(anim_state(), anim_phase())` 就是将来 `SpriteFrames` 的动画名 + 帧进度；
> `enemy_rig.gd` 整份删除，`enemy.gd` 只换 `_draw()` 里 `_rig.apply/solve` 那一段。
> AI / 三相位状态机 / 霸体 / 贴地预警 / 判定全不动。

### 朝向模型（v0.5 的核心，`scripts/combat/facing.gd`）

朝向是**世界空间**的单位向量，不是屏幕方向 —— 屏幕 Y 是被压扁过的纵深，直接拿它当朝向会
在跳起来/被推飞时读错。四个常量刻意避开 Godot 的 `Vector2.UP`：

| 常量 | 世界向量 | 含义 | 画法 |
|---|---|---|---|
| `Facing.RIGHT` | `(1, 0)` | 朝右 | 侧视（镜像源自这张） |
| `Facing.LEFT` | `(-1, 0)` | 朝左 | 侧视镜像 |
| `Facing.UP` | `(0, +1)` | 世界 +z = **屏幕上方** = 画面里侧 | **背面**：头发盖满整颗头 + 发髻，无五官 |
| `Facing.DOWN` | `(0, -1)` | 世界 -z = **屏幕下方** = 镜头这侧 | **正面**：刘海 + 两只眼 |

- **`Facing.choose(current, world_dir, ratio)`** —— 唯一允许改朝向的入口。规则：无输入保持；
  同一根轴（含反向）立即转；跨轴要求 `新分量 > 当前分量 × ratio(1.25)`。这条迟滞是手感，
  不是优化 —— 没有它，斜向走位时朝向会每帧翻一次。
- **`Facing.perp(u) = (-u.y, u.x)`** —— 右手方向。`AttackShape` 的局部坐标系就是 `(u, perp(u))`，
  所以形状永远按「朝右」定义一次，四个方向都靠旋转，**没有四套分支**。
- **形状 → 屏幕**：局部偏移要过 `_local_to_world()`（**逆**旋转）再压扁。这里踩过一次坑：
  把正向的 `_to_local()` 用了两遍，朝右时是恒等、朝左时凑巧等价，**只有上下会整整歪 90°**，
  且预警和判定一起歪 —— 不会报错，只是站对位置的人打不到（细节见 PROGRESS 的 v0.5 一节）。
- **美术成本**：一个动作 = 3 套唯一图（侧视 + 背面 + 正面），侧视镜像出左右。
  M0 锚图因此要出 **3 张视图**，不是 1 张侧视。
- **不做斜向（45°）**（2026-10-30 决定，推翻此前的八向计划）。理由是**玩法可读性**：
  攻击方向和格挡半平面都靠 4 根轴才一眼看得懂，八向会把格挡变成 90° 锥。
  而且判定层本来就只有 4 个朝向 —— 不加斜向**不用改任何代码**；要加则要动
  `Facing.choose` 的吸附表、8 个形状朝向和 4 形状 × 8 朝向的测试矩阵。
  代价只是斜走时的 45° 滑步观感，由 1.25 迟滞 + 出招锁朝向压住。
  > 若将来走 3D 预渲染路线，斜向只是「相机多转 45°」，届时换吸附表即可，形状系统不动。

### 攻击范围 = 每个招式自带一个形状（v0.4 核心机制）

用户的原话（仍然是验收标准）：

> 「范围攻击就是在 x 和在纵深轴画一个范围，可以是圆形（应该是椭圆形更准确）、扇形，矩形。
> 比如横劈动作就是一个扇形，扇形区域内的敌人或者玩家（敌人发起的动作）会受到伤害。
> 可以做一个横批的攻击（敌人也做上），再给玩家来一个技能，可以在玩家面朝方向一定距离的圆形
> （视角内椭圆形？）造成伤害，就是闪电从空中落下然后在区域内造成伤害」

> 「敌人的攻击可以是一个横向轴的单独判断，也可以是一个范围工具，就是在它的攻击范围内，
> 离他几根横向轴上都会收到攻击」

实装为 [scripts/combat/attack_shape.gd](scripts/combat/attack_shape.gd)（`AttackShape`，`Resource`）：

| 形状 | 用法 | 当前实例 |
|------|------|---------|
| `RECT` | 身前一条窄而远的长条 | 玩家重击：长 96 × 纵深 52 |
| `ARC` | 贴着身扫一片（半径 + 张角） | 玩家横劈：r=66 / ±75°；**敌人横扫：r=54 / ±60°** |
| `CIRCLE` | 一个点周围的圆（可带偏移） | 落雷：r=46，圆心在身前 132 处 |
| `band(min, max)` | 叠加**离地高度带** | 敌人横扫：`band(0, 40)` —— 跳过去就躲得开 |

三条与形状绑定的不变量（**改了会静默出错**）：

1. **一招 = 一个 `AttackShape` 实例。** 起手预警、`CollisionShape2D`、自检读的都是它 →
   「地上画的范围」和「真的会打到你的范围」在结构上不可能漂移。
2. **`origin` 永远是攻击者的脚底。** 形状自己的 `offset` 决定圆心在哪，物理体的
   `collision_offset(facing)` 决定碰撞体中心。**两处都偏 = 偏两次。**
3. **靶子的碰撞体必须活在地面平面上**（`BeltSpace.ground_circle_shape`）。
   用 `CircleShape2D` 的话，屏幕正圆在地面平面里是一个**纵深翻倍**的椭圆 ——
   表现是「站在扇形外面一格半照样掉血」。

**四向朝向怎么接进形状（v0.5）：** 形状**只按「朝右」定义一次**。判定时把偏移化到局部系
`(世界偏移 · u, 世界偏移 · perp(u))`，于是「朝哪边」只影响这一个点乘，没有四套分支。
两个例外必须单独处理：`RectangleShape2D` **永远是轴对齐的**，纵向朝向下要交换宽高；
预警/物理体的顶点则要过**逆变换** `_local_to_world()` 再压扁（用反了会整整歪 90°，见「朝向模型」）。
自检用「4 形状 × 4 朝向」的逐点扫描（数学 ⇔ 物理体 ⇔ 预警多边形）兜住这一整类错。

### 敌方的攻击形状

敌人横扫 = 低空扇形。**高度带是加跳跃的主要收益**：没有它，跳跃在地面战斗里只是一个好看的位移。
判定点放在**受击方**（Area2D 活在 2D 平面，表达不了离地高度）：

- 敌人打玩家 → 玩家的 Hurtbox 用自己的 `height` 查；
- 玩家打敌人 → `AttackHitbox._try_hit` 读敌人 body 的 `height`。

两条链路对称，都由「谁受伤谁查」这条老约定控制。

### 技能系统（核心卖点：多种方式打怪）

**目标：让玩家构筑自己的打法。** 分三层：

1. **招式（近战武学）**：剑法/刀法/枪法等，改变轻击重击的连段和效果
2. **法术（远程/控制）**：飞剑、剑气、符箓、阵法——远程伤害、AOE、控场
3. **法宝（特殊机制）**：主动释放的强力道具，如飞剑自动索敌、护体罡气、瞬移

| 层 | 举例 | 对应打法 |
|----|------|---------|
| 招式 | 快剑（攻速快）/ 重剑（高伤破防）/ 枪（长手范围）| 近战流派 |
| 法术 | 飞剑索敌 / 剑雨 AOE / 定身符 | 远程/风筝流派 |
| 法宝 | 护体罡气 / 影分身 / 御剑飞行 | 特殊玩法流派 |

> **构筑逻辑**：装备决定「招式」和基础数值，技能槽位（主动）+ 词条（被动）决定「怎么打」。
> 同一套装备 + 不同技能 = 不同打法。**用少量装备 × 大量技能组合，代替几百件装备**，解决内容消耗问题。
>
> 每个新技能在代码里就是一个**新的 `AttackShape` 组合**（形状 + 偏移 + 高度带 + 延迟），
> 不需要新的判定框架。

#### v0.9 技能 = 一行数据（`scripts/combat/skill_def.gd` · `skill_book.gd`，2026-11-13）

v0.8 之前，一个技能 = `player.gd` 里一组 `@export` 数值 **+ 一个专属施放函数**。
加第四个技能要同时动四处：状态机（怎么进 `ATTACKING`）、冷却计时器、动画选择、输入绑定 ——
而「这个技能是什么」本该只是一份数据。

现在：**技能 = 一个 `SkillDef` + 一个输入绑定**。`family` 决定玩家侧怎么执行：

| family | 执行 | 当前技能 |
|---|---|---|
| `STRIKE` | 生成一个 `AttackShape` 判定框（可带延迟） | 落雷 |
| `BUFF` | 给自己挂一个持续计时器 | 护体罡气 |
| `PLACE` | 在地上放一个留在原地的阵 | 剑阵 |

状态机只认 `family`，**不认技能名**。施法姿态来自表里的 `cast_anim`，冷却统一记在
`_cooldowns: Dictionary`（键 = `SkillDef.id`）—— 原来三个「每技能一个计时器变量」的写法删掉了。

- **标签用位标志**（`TAG_UNBLOCKABLE` / `TAG_ARMOR_BREAK` / `TAG_DOT`），不用每个技能加一堆 bool。
  加新机制时不改任何既有技能的构造代码，「没有标签」就是一个 `0`。
- **`make_shape()` 是形状的唯一来源**，`player.skill_shape()` 只是转调它 —— 表里写的范围和打得到的范围不可能漂移。
- **五行 + 毒目前只是身份**（`Element`），反应表是下一步；本轮只把第一个标签打通到判定层。
- **为什么先不写 `.tres`**：现在三个技能是代码原语，数值和实现要一起改。等内容量上来
  （6 流派 × 5 技能）再给字段加 `@export`、换成资源文件 —— 消费方读的是同一组字段，换存储不动 `player.gd`。

#### 不可格挡（COMBAT_MATRIX §3 ② 的第一个标签）

`EnemyAttack.unblockable` → `player.take_damage(..., unblockable)` → `_resolve_guard` 第 ⓪ 条直接放行。
它让格挡从「万能解」变回「多数时候的解」，**但只豁免格挡**：

- **闪避（无敌帧）、跳跃（高度带）、护体罡气（免伤）全都照常有效** —— 不可格挡 ≠ 必中，它只是要求换一个答案。
- **不扣格挡精力、不走精准窗口**：举着一个对这一招无效的盾，不该再让玩家赔一次精力
  （那会被读成「挡漏了」，而真相是「这招本来就挡不住」）。
- **颜色是玩法信息**：橙红 = 可格挡，**紫红 = 挡不住**。`EnemyAttack.WARN_COLOR` / `UNBLOCKABLE_COLOR`
  是唯一来源，贴地扇形、敌人身体/眼睛、命中帧、HUD 提示行全部读它 —— 任何一处自己写死一个红，
  玩家就会在两套配色之间学到矛盾的信息。

## 技术实现（Godot 4.6）

### 视角与渲染分层

| 技术点 | 实现 |
|--------|------|
| 地面 | `belt_floor.gd` 程序化平铺条带（不是 TileMap / TileSet） |
| 角色 | `_draw()` 几何占位，**四向**分三种画法（侧视 / 背面 / 正面；左右靠镜像） |
| 纵深压缩 | 世界 z → 屏幕 y × 0.5（`BeltSpace.DEPTH_SCALE`） |
| 深度排序 | `y_sort_enabled = true` —— 屏幕 Y 就是纵深 |
| 移动 | X + Z 两轴独立，速度用**世界单位**、上限在世界空间截断 |
| 碰撞 | `CharacterBody2D` + 贴地椭圆（`ConvexPolygonShape2D`） |
| 攻击判定 | 短命 `Area2D` + `AttackShape` |
| 摄像机 | `Camera2D` 跟随 + 从地面推导边界 + trauma 震屏 |

**图层顺序（绝对 `z_index`，先于 y-sort 结算）：**

```
Backdrop(-20) < Floor(-10) < 贴地预警 GroundTelegraph(-5) < 角色/刀光(0) < Fx(40)
```

> ⚠️ 贴地层必须 `z_as_relative = false`。开着的话 `z_index` 相对父节点结算，
> 而父节点在 0 —— 减出来还是 0，**静默失效**。
>
> 起手预警必须垫在角色**下面**：玩家要看的是「**我的脚**在不在里面」，被身体盖住的正是最关键的那块。
> 命中帧的闪光则故意留在角色层（要看「谁从哪边打的我」）。

**碰撞层（bit 定义，全项目一致）：**

| bit | 用途 |
|-----|------|
| 0 | 玩家身体 |
| 1 | 敌人身体 |
| 2 | 玩家攻击 |
| 3 | 敌人攻击 |
| 4 | 墙壁 / 障碍 |
| 5 | 交互物 / 复活点 |

### 角色体积：世界空间软分离，不是物理层（v0.4 修复）

**症状**：敌人会追到玩家身上**完全重合**，然后高频抖动。

**两个根因，各自都不报错：**

1. 两个角色的 `collision_mask` 都只有墙（`1<<4`）—— 角色之间根本没有碰撞；
2. 追击条件原来是 `dist > 1.0`，等于几乎追到中心点才停 → 穿过 → 方向翻转 → 再穿回。

**为什么不开 layer/mask 互撞**：`CollisionShape2D` 活在**屏幕**空间，而「两个人有没有占同一块地」
是个**世界**问题。屏幕 y 走 1 格，世界里是 2 格纵深 —— 直接互撞会停在「画面上贴着、世界里差一格」的位置。
这和攻击判定踩的是同一个坑。（改玩家身体形状也不行：它和边界墙的摆位是配套调出来的。）

**实装**：[scripts/body_separation.gd](scripts/body_separation.gd)

- 世界平面上的圆-圆分离，最小间距 = `body_radius()` 之和（玩家 12 + 敌人 11 = 23）。
- **由 `main.gd` 每物理帧统一调一次**，`process_physics_priority = 100` —— 跑在所有角色的
  `move_and_slide()` 之后，改的已经是本帧最终位置。一对角色只结算一次（各推一次 = 推开两倍）。
- 谁让路由**速度**决定：正在往里挤的那个退出去；都没在动（出生/瞬移重叠）就对半分。
- 敌人追击改为在 `chase_stop_distance = 30`（世界单位）**线性减速刹车**，不再往身上挤；
  这个数必须 > 身体半径之和，否则等于没停。
- `BODY_RADIUS`（站多近）和 `HURTBOX_RADIUS`（打不打得中）是**两个数**，不要合并。

自检 7 条：契约 · 完全重合一帧分开 · 追击全程不重合 · 能停稳 · 停稳后不抖 · 顶着走穿不过去 · 保持最小间距。

### 打击感四要素（0 素材成本）

| 要素 | 做法 | 成本 |
|------|------|------|
| 屏幕震动 | Camera2D offset Tween，重击 4px 轻击 1px | 0 |
| 击停帧 | 命中瞬间双方暂停 0.05-0.1s | 0 |
| 粒子特效 | 命中火花、剑气拖尾、受击碎片 | 0（程序化） |
| 音效 | 挥剑/命中/格挡/死亡声 | 需素材 |

### 两道闸门 + 一层截图

```bash
GODOT="D:/Godot/Godot_v4.6.3-stable_win64_console.exe"
P="C:/Users/Administrator/Desktop/monorepo/apps/game/blitz"

# 闸门 1：解析 (⚠️ Godot 报错也返回 0 —— grep 是闸门, 空输出才算过)
"$GODOT" --headless --path "$P" --editor --quit 2>&1 \
  | grep -nE "SCRIPT ERROR|Parse Error|ERROR|Failed to load|WARNING"

# 闸门 2：自检
"$GODOT" --headless --path "$P" --quit-after 3000 -- --smoke 2>&1 \
  | grep -E "❌|自检结束"

# 第三层：截图 (自检看不见渲染, 这层不能省; 不能 --headless)
"$GODOT" --path "$P" -- --shots --zoom=3 --focus=40,-2   # 落雷为主
"$GODOT" --path "$P" -- --shots --zoom=3 --focus=0,0     # 剑阵为主
```

自检覆盖 347+ 项（**以自检报告打印的实际数字为准** —— 这里不写死，免得每次加断言都要回来对一遍），按组：

- **场景/坐标**：装配 · 相机边界 · 障碍碰撞体非零 · 边界墙拦人 · 坐标桥往返 · 压扁比 2:1
- **高度轴**：按跳能离地 · 重力**不改** `global_position.y` · 落地 height 精确归零 · 受击不能跳 · 纵深输入不转身
- **形状**：RECT 纵深边界 · ARC 角度与纵深容差（随位置变化，不是常数）· CIRCLE 偏移 · 高度带 · 玩家横劈纵深比敌人更宽
- **战斗**：格挡正面免伤 / 背后掉血 / 垂直于朝向算正面（左右上下都验）· 精准窗口（命中/过期/自动关闭）· 举盾不改朝向 · 破防门槛 · 蓄力破霸体 · 霸体不被打断 · 蓄力中受击不卡死
- **朝向**：四向吸附 + 1.25 迟滞（无输入不变 / 同轴立即转 / 跨轴看大小）· 形状在四个朝向下「数学 ⇔ 物理体 ⇔ 预警多边形」逐点一致

### 人工验收（自检证明不了，必须 F5）

1. **横向对得上了吗** —— 按 D 向右走，脚下地砖跟人一起动、不再斜着错开
2. **跳跃读得出来吗** —— 起跳/滞空/落地三阶段，影子有没有留在原地当参照
3. **攻击范围看得见吗** —— 敌人起手时地上那片扇形，是不是一眼就知道该站哪（它必须画在角色**下面**）
4. **纵深容差合适吗** —— 站在敌人上下一点点，该中招吗？会不会太宽容
5. **跳跃躲得开吗** —— 跳起来躲低扫，是不是个有意义的操作
6. **精准格挡有回报感吗** —— 金色爆闪 + 敌人硬直，是不是立刻想反打
7. **精力逼出取舍了吗** —— 是否出现过「想闪但精力不够」的时刻
8. **破防够痛吗** —— 精力见底被打崩，是否让你下次不敢硬挡
9. **角色能互相顶住吗** —— 顶着敌人走会不会穿过去？敌人贴住你之后还会不会抖？（v0.4 修复项）
10. **落地硬直 0.18s 合适吗** —— 跳完横扫还来不来得及补一刀？是「没站稳」还是「卡住了」？（0.12~0.25 之间试）
11. **罡气读得懂吗** —— 开罩/挡下爆散/到期闪烁三个阶段能分出来吗？开着罩打不出招会不会让人以为卡了？
12. **剑阵的「逼位」看得出来吗** —— 落阵后追兵是不是明显绕了弧线？绕行像「聪明地绕」还是像「卡住了」？
13. **剑阵的「选择」成立吗** —— 敌人是宁可挨跳伤也硬闯，还是干脆不进来？两种都不对的话调半径/跳伤间隔。
14. **站在自己阵里是不是个陷阱** —— 敌人有没有照样冲进来打你？如果它绕着圈不打你，③ 那条规则就写反了。
15. **3 秒 / 4.5 秒冷却合适吗** —— 阵消失时你是「该再放一个了」还是「才刚放完」？
16. **敌人的起手读得出来吗** —— 故意不看地上的预警圈，只看身体：后仰 + 收爪 + 张嘴，是不是一眼就知道「要打了」？
17. **两种硬直分得开吗** —— 短硬直（往后一震）和长硬直（重心下沉、爪撑地）会不会看混？长硬直该像「反击窗口」而不是「卡死了」。
18. **紫红预警读得出来吗** —— 不看 HUD 那行字，只看颜色：能不能在起手当下分出「这个能挡 / 这个挡不住」？紫红出现时你第一次是不是下意识按了格挡（按了也正常，关键是挨完之后有没有改动作）？

## 设计原则

1. **玩法第一** — 手感调好了再加美术和内容
2. **纯代码先行** — 原型不需要外部素材，`_draw()` 几何图形验证
3. **资源是灵魂** — 仙侠的爽点是「积累变强」，掉落和成长要做好
4. **操作高频 + 反馈强** — 精力系统 + 打击感 > 招式数量
5. **少装备多组合** — 用技能构筑代替海量装备，省内容
6. **可测试** — 任何时候 F5 都能跑；自检 + 截图探针是两道自动化闸门
7. **边做边写文档** — 脚本标注学习文档引用，双向关联
8. **画的就是判的** — 一切范围必须同源（一个 `AttackShape`），禁止两处各算一遍
