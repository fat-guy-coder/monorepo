## 0. 一句话

一个**不规则的房间**、一个玩家（idle / 走 / 跳 / 横劈 / 纵劈 + 三个技能）、一个小兵（走 / 跳 / 后侧步 + 2~3 套攻击 + 3 种受击）、一个 Boss、一套 HP / 气力 / 蓝条 UI。全部用正式像素资产，**全屏**运行。

## 2. 两个新要求（先改地基）

### 2.1 全屏：填满屏幕，不是 1280×720 小窗

**目标**：启动即全屏；窗口比例变化时画面跟着变，不留黑边；UI 贴屏幕边缘。

**方案**：

| 项 | 值 | 理由 |
|---|---|---|
| 设计分辨率 | 1280×720 | 现有素材、数值、相机都按它标定 |
| 窗口模式 | 无边框全屏（`mode=3`） | 启动即全屏；F11 可切回窗口 |
| 拉伸模式 | `canvas_items` | UI 和世界一起缩放，像素游戏常用 |
| 比例策略 | `expand` | **不裁切、不加黑边**，多出来的空间显示更多世界 |
| 纹理过滤 | Nearest | 像素不糊 |
| 像素吸附 | transforms + vertices | 减少半像素抖动 |

**为什么不是 `keep`**：`keep` 会加黑边，正是你说的「限制在长方形」的观感。
`expand` 在 21:9 上显示更宽的世界，在 16:10 上显示更多上下背景 —— 对横版是好事。

**代价（必须知道）**：1280×720 的设计分辨率在 1920×1080 上是 **1.5×** 缩放，
像素不是严格 1:1，个别像素会 1px/2px 交替。三条路：

| 方案 | 观感 | 代价 |
|---|---|---|
| **A. 接受 1.5×（先按这个做）** | Dead Cells 也不是严格像素对齐；远看没问题 | 近看有轻微不均匀 |
| B. 整数缩放 + 黑边 | 像素绝对干净 | 回到「长方形小窗」，和你的要求冲突 |
| C. 设计分辨率提到 1920×1080 | 1080p 下 1:1 最清晰 | 角色要按约 168px 重画，素材量增加 |
| D. 640×360 + 整数缩放 | 2×/3×/4× 永远干净 | 像素网格变粗，角色只有 56px，达不到「精美」 |

> 补充：`expand` + 720 基准高度在 **720p = 1×、1440p = 2×、4K = 3×** 都是整数缩放，
> 只有 **1080p = 1.5×** 是分数。先接受，等第一个角色进游戏后用 1× 和全屏截图对比再决定要不要转 C。

**项目设置（Godot 4）**：

```ini
[display]
window/size/viewport_width=1280
window/size/viewport_height=720
window/size/resizable=true
window/size/mode=3
window/stretch/mode="canvas_items"
window/stretch/aspect="expand"

[rendering]
textures/canvas_textures/default_texture_filter=0
2d/snap/snap_2d_transforms_to_pixel=true
2d/snap/snap_2d_vertices_to_pixel=true
```

**代码要改的地方**：

1. `main.gd::_viewport_size()` 不能再读项目设置的 1280×720 —— 全屏 + `expand` 后逻辑视口会变。
   改成读 `get_viewport_rect().size`，并监听 `get_viewport().size_changed`。
2. `CameraRig.fit_to_floor()` 在每次视口尺寸变化时重算，否则窗口一变边界还是旧的。
3. `Hud` 里写死坐标的元素改成 **锚点**：HP / 气力 / 蓝条贴左上，技能栏贴底部居中，Boss 血条贴顶部居中。
   `CanvasLayer` 不参与世界缩放，但 Control 必须用 anchors，不能用固定 `position`。
4. 加 `toggle_fullscreen` 输入（F11），用 `DisplayServer.window_set_mode()` 切换。
5. 相机纵向仍然锁死（见 2.2），所以全屏多出来的高度显示背景，不会露出「房间外面」。

**验收**：

- 16:9 / 16:10 / 21:9 三种比例下画面都填满，没有黑边
- 窗口拉伸时角色不会跑到边界墙外面
- UI 始终贴边，不随世界滚动
- F11 来回切换，相机边界正确

### 2.2 不是长方形：可行走区域用「格子掩码」

**目标**：房间不是四堵墙围出来的矩形，可以是 L 形、凹形、洞穴、带缺口的大厅；
地面只铺在有内容的地方。

**方案**：把 `BeltFloor.fill_rect()` 换成 **格子掩码（walkable mask）**：

- 一张二维布尔表：每个格子是「可走」还是「虚空」
- 地面只画可走的格子；边缘格用「悬崖边」变体
- 碰撞不靠四堵墙，而是沿「可走 ↔ 虚空」的边界生成薄墙
- 相机边界用**单独的包络矩形**，不等于可行走区域的外接框

**为什么用掩码，不用多边形**：

| 方案 | 优点 | 缺点 |
|---|---|---|
| **格子掩码（推荐）** | 好画（ASCII/编辑器）、碰撞精确、和现有 TileMap 一致、天然轴对齐 | 边缘是阶梯状，需要美术用悬崖/暗边盖住 |
| 手绘多边形 | 边缘是斜线，更自然 | 碰撞、铺砖、相机都要另写一套；和 64×32 网格对不上 |

**作者格式**：先支持 ASCII，改关卡不用开编辑器：

```
....................
....########........
....########........
....####............
....####....######..
....####....######..
....##############..
....................
```

- `#` = 可走
- `.` = 虚空
- `S` / `E` / `B` / `P` 可分别标记出生点、小兵、Boss、道具（可选）

**碰撞生成**：

1. 遍历每个可走格，检查上下左右四个邻居
2. 邻居是虚空 → 在这一侧生成一段薄墙（`RectangleShape2D`，厚 16~22px，bit4）
3. 同一直线上相邻的段**合并成一条长墙**，减少节点数
4. 水平段和垂直段在拐角处各外延半个厚度，补住缝隙

> 为什么不用 `SegmentShape2D`：线段没有厚度，高速移动有穿透风险；
> 薄矩形和现有墙一致，`move_and_slide` 更稳。

**相机包络**：

- `BeltFloor.walkable_bounds()` = 可走格的外接矩形（铺背景用）
- `BeltFloor.camera_bounds()` = **单独**的相机包络（默认 = 外接矩形外扩一圈；
  L 形房间可以手写一个更紧的矩形）
- `CameraRig.fit_to_floor()` 改用 `camera_bounds()`
- 如果房间凹口很大，相机会拍到虚空 —— 由背景层盖住；后续可升级成「多矩形相机区」

**硬约束：纵深不超过 18 格（576px）**

不管房间多不规则，**可走区域的最大纵深必须 ≤ 18 格**。
原因在 `main.gd` 的注释里：纵深一旦超过 720px，相机会开始上下滚，
横版的观感就变成了平台跳跃。全屏 `expand` 后逻辑高度只会 ≥720，这条只会更安全。

> 如果以后要做更深的洞窟，正确做法是**切房间**，不是把纵深拉长。

**v1 地面是平的**：掩码只决定「能不能走」，不表示高低差。
悬崖边是视觉，掉不下去。高低差 / 平台是后续版本的事。

**代码要改的地方**：

| 文件 | 改动 |
|---|---|
| `belt_floor.gd` | `fill_rect()` → `fill_mask()` / `load_ascii()`；加 `is_walkable()`、`walkable_bounds()`、`camera_bounds()`、`edge_runs()` |
| `main.gd` | `_build_floor()` 读房间数据；`_create_border_walls()` → `_build_boundary_collision()`；`_build_backdrop()` 用 `camera_bounds()` |
| `camera_rig.gd` | `fit_to_floor()` 改用相机包络；视口变化时重算 |
| `smoke_test.gd` | 新断言：掩码外不可走、边界墙拦人、相机不拍到可走区外、视口变化后边界正确 |
| `debug_overlay.gd` | 画出掩码边界和相机包络 |

**验收**：

- 走进凹口 / 死胡同，不会穿墙
- 房间边缘是可见的悬崖 / 暗边，不是一条隐形的墙
- 相机不会停在「一半是虚空」的位置
- 16:9 / 21:9 下都能看到完整的可走区域

### 2.3 如果你说的「不是长方形」是指画面外框

屏幕本身永远是矩形。能改的是**取景框的装饰**（暗角、卷轴边、雾气遮罩），
那是 UI overlay，不影响可行走区域。这一层可以后加，不阻塞上面的方案。

## 3. 先定风格，还是先建模？

**先定风格，但顺序是：风格锚 → 资产规格表 → 灰盒 → 管线验证 → 量产。**

不要「定完风格就直接 Blender 建模」。原因：

1. **机位是风格的一部分**，不是建模时才决定的。yaw / pitch / 正交 / 画布尺寸一旦变了，所有模型都要重渲。
2. **帧数和命中帧由玩法决定**。轻击现在是 0.15s，撑不住 7 帧动画；要先调到 0.28~0.32s，才能定「第 3 帧命中」。
3. **房间形状和全屏比例会改变构图**。先灰盒跑一遍，确认相机、掩码、UI 都在正确的位置，再让美术去贴合。

**风格锚（M0）要锁死的数字**：

| 项 | 值 |
|---|---|
| 机位 | 正交侧视，yaw 0°，pitch 0~5°，全项目锁死 |
| 像素密度 | 1 美术像素 = 1 设计像素（1280×720 基准） |
| 角色高 | 玩家 112px / 小兵 80px / Boss 192px |
| 画布 | 玩家 192×192 / 小兵 128×128 / Boss 320×320 |
| 枢轴 | 脚底中点 |
| 调色板 | 32~48 色，左上光源，1px 深色描边 |
| 抗锯齿 | 禁止 |
| 动画 | 原地，不烘根位移 |

> 如果纯侧视太扁，可以改成渲染左右两个角度（±12°），3D 下多渲一套很便宜；
> 但要同时放弃 `flip_h` 镜像，代码里按朝向选动画。

## 5. 流程（M0–M7）

```
M0 风格锚 + 规格表
      ↓
M1 灰盒：全屏 + 非矩形房间 + UI 草图 + 玩法改动清单
      ↓
M2 3D 管线验证：玩家 idle + 横劈，进游戏
      ↓
M3 像素管线验证：地砖 + 刀光，1× 汇合验收
      ↓
M4 玩家全动作 + 小兵 + 受击反应
      ↓
M5 三个技能 + 蓝条 + VFX
      ↓
M6 Boss + 房间美术 + UI
      ↓
M7 命中帧 / 打击感打磨 + 验收
```

| 阶段 | 产出 | 时间 |
|---|---|---|
| M0 | `art/style_bible/`（palette / rules / prompts / references）+ 规格表 + manifest 模板 | 2~3 天 |
| M1 | 全屏设置、掩码房间、边界碰撞、相机包络、UI 锚点、玩法清单 | 2~3 天 |
| M2 | 玩家 base mesh + 绑骨 + idle / 横劈 + Blender 渲染脚本 + 进 Godot | 4~6 天 |
| M3 | 地砖 + 刀光 + 调色板量化 + 1× 汇合验收 | 3~4 天 |
| M4 | 玩家全动作 + 小兵全动作 + 三套受击 + 接入状态机 | 1.5~2 周 |
| M5 | 雷电 / 巨剑 / 树根 + 蓝条 + 技能 UI | 1 周 |
| M6 | Boss + 房间美术 + 完整 UI | 1.5~2 周 |
| M7 | 命中帧对齐、震屏、顿帧、击退、验收 | 3~5 天 |

**M2 / M3 的意义**：各用一个最小样本把两条管线跑通。跑通之前不要量产；
跑不通就换路线，成本只有一周。

**顺序上的一个反直觉点**：先做 M1 灰盒，不是先做美术。
因为要验证的是「全屏 + 非矩形房间 + 技能行为」，这些会改变构图和帧数。
先画完再改，返工的是最贵的那部分。

## 7. 动画接入约定

- `AnimatedSprite2D` 挂在角色节点下，**脚底原点**；`offset` 让脚底落在 `(0, 0)`
- 保留 `_draw()` 占位作为 fallback（`use_sprite` 开关）
- 跳跃只改精灵层的 `y = -height`，影子留在地面
- 朝向用 `flip_h`（纯侧视）或按朝向选两套动画（±12° 方案）
- 动画**原地**：位移、击退、冲刺由代码管
- `SpriteFrames` 的 fps 和命中帧写进 manifest；游戏用 `speed_scale` 对齐实际时长
- 攻击时长按战斗时序重调：轻击 0.28~0.32s，重击 0.45~0.55s
- 接触阴影独立节点，不烘焙进帧

## 8. 验收标准

1. 全屏启动，16:9 / 16:10 / 21:9 都填满，无黑边
2. 非矩形房间：凹口、死胡同、边缘都能正确阻挡

9. 60fps（2D 精灵 + 少量碰撞体）

## 9. 风险

| 风险 | 应对 |
|---|---|
| 第一个盒子范围太大 | M1 只做「一个玩家 + 一个小兵 + 一个房间」的可玩闭环；Boss / 技能后置 |
| 3D 管线拖时间 | M2 只做 idle + 横劈；4 周内跑不通就换路线 |
| 非矩形碰撞有缝 | 薄矩形 + 拐角外延 + 自检；先在灰盒里走一圈 |
| 1.5× 缩放不锐利 | 先接受；M3 用 1× 和全屏截图对比后再决定是否提分辨率 |
| 玩法没跟上 | 第 6 节清单先做，不要等美术 |
